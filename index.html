How it works

It checks what shipped, not what might be called

A VEX statement can say vulnerable code doesn't matter in two ways, and they claim different things. Reachability tools read your source and infer whether the code could ever run. vexproof asks a simpler question: did the bundler put it in the output at all? If it didn't, the code isn't unreachable, it's absent.

vexproof

code_not_present

The vulnerable code isn't in what shipped. The bundler's record of its output shows it.

Rests on
The bundler's record of every file it emitted, attached to the statement
To check it
Look for the file in the build output
Wrong when
The record misses part of the build, so vexproof stops when a shipped file isn't in it

Free answers at the package level. Pro goes on to the file level, and keeps the decisions people make.

Anything it can't prove stays in_triage, with the reason: vulnerable file(s) bundled: omit.js. A person decides, and vexproof review records it.

Safeguards

Why trust a build record with a security claim?

Because vexproof checks the record before it believes it. A wrong "not affected" is worse than saying nothing, so every statement carries its evidence, and vexproof stops and tells you why when:

  • A shipped file is missing from the build record. On Gitea this caught two bundles from nested builds.
  • A stats file leaves modules out, as rspack build --json does whatever the config says.
  • A package ships twice and one copy's version can't be read.
  • The app runs on a server it hasn't seen. For Next.js, Nuxt and similar, pass the deployment; bundled server code needs source maps.
  • No rule covers the advisory. Rules derived from a fix only suggest a verdict until a person accepts them. Checked against the hand-written rules on 841 npm advisories, derived rules never cleared a finding the hand rules kept open.

What a verdict actually says

A not_affected statement says the vulnerable code is not present in the artifact you named: the browser bundle, or the server deployment. It says nothing about code that runs at build time, in a dev server or in a CI script, and vexproof never widens the claim on its own. "Not shipped" is a narrower claim than "not exploitable", which is why it can be proven.

Reviews

Decide once, not every release

When vulnerable code does ship, a person decides whether it can be reached. Most tools tie that decision to a version, so every dependency bump asks again. vexproof ties it to what the decision rests on: the shipped vulnerable files, and the code that imports them.

A review keeps the reviewer, the date and the reasoning. One review covers every advisory on the same vulnerable files. Decisions that rest on things vexproof can't see, like a gateway rule, stay tied to the exact version, and every review is re-confirmed after a year.

Server apps

Apps with a server, too

For Next.js, Nuxt and other apps that render on a server, vexproof reads what you deploy: the package files the framework copied into its output, and the source maps of its bundled code. A file that isn't deployed can't run, so the claim is the same one it makes for a browser bundle.

Compare

How it fits with what you have

vexproof doesn't replace your scanner or reachability platform. It reads what they report and writes VEX they apply, as a CLI or a GitHub Action. Every statement carries both the CVE and GHSA IDs, so the same file works in Trivy, Grype and Dependency-Track. GitHub's Dependabot reads no VEX, so the Action can also dismiss the alerts a run settles.

FAQ

      

        
Questions people ask

        

          Our scanner or reachability platform already suppresses these. Why add this?
          
Keep it. Reachability infers whether code could be called; vexproof shows whether it shipped at all, which is the stronger claim and the easier one to verify. The practical difference is where the answer lives: a platform keeps its conclusions in its own dashboard, while vexproof writes a standard VEX file that Trivy, Grype and Dependency-Track apply and that a customer or auditor can read. If nobody outside your team ever asks for evidence, the dashboard may be enough.

        

        

          Does anything leave our network?
          
Your code and your build output never do. vexproof runs in your CI with no account and no telemetry, it never contacts us, and the license is a signed key checked on the runner. It is not fully offline, though. It looks things up in two public databases: OSV, to find advisories or match GHSA and CVE IDs, and the npm registry, when you derive rules from advisory fixes. Those requests carry package names, versions and advisory IDs. If you turn on Dependabot dismissal, it also calls GitHub's API for your repository's alerts. If you pass a findings file and skip alias lookup, a run makes no network calls at all.

        

        

          Is it open source?
          
The core is: the CLI, the bundler plugins, package-level verdicts and both VEX formats are MIT, and they run on their own. The Pro features ship in the same npm package, in one folder, src/pro/, under a separate commercial license. You can read that code and install it freely, and using it needs a key. Without a key it only counts what Pro would settle. How the code is licensed

        

        

          "Not shipped" isn't "not exploitable". What about build-time code?
          
Correct, and vexproof doesn't claim otherwise. A verdict covers the artifact you named: the browser bundle, or the server deployment. Code that only runs at build time, in a dev server or in a CI script is out of scope, and a package used that way stays open unless you review it yourself. For apps with a server, vexproof refuses to speak for the browser bundle alone.

        

        

          How do you know the rules are right?
          
Hand-checked rules name their source advisory and the files holding the vulnerable code, and they're versioned in the open. Rules derived from an advisory's fix only suggest a verdict until you accept them. Checked side by side on 841 npm advisories, derived rules never cleared a finding the hand rules kept open. When no rule covers an advisory, the finding stays open.

        

        

          Why now?
          
The everyday reason: the same findings stop being re-triaged every sprint. The regulatory one: the EU Cyber Resilience Act's reporting duties began on 11 September 2026, with the full requirements, SBOMs included, from 11 December 2027. Answering "does this CVE affect us?" in hours means already knowing what you ship, and enterprise buyers now ask for the same evidence in procurement.

        

        

          We have more than 500 employees. What does Pro cost?
          
Up to 500 employees, Pro is $1,200 per year. Above that, let's talk: we price it for the part of your company you want covered, whether that's the whole company or one subsidiary or division that buys for itself. It's still one yearly price, never per seat, and open-source projects get Pro free at any size.

        

        

          JavaScript only?
          
Yes. The proof depends on a bundler recording exactly which files it emitted, and that record exists for JavaScript and TypeScript builds. It's also where the noise is worst: a typical frontend installs far more than it ships. Other languages are out of scope, and there's no plan to become a multi-language platform.
