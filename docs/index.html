Guide

vexproof documentation

Your scanner reports vulnerabilities in every package your lockfile installs. vexproof checks each finding against what your production build actually shipped. When the vulnerable code isn't in the bundle, it writes a not_affected statement with the evidence. Anything it can't prove stays open, with the reason.

The statements are VEX (Vulnerability Exploitability eXchange): a machine-readable record, per vulnerability and per product, of whether the product is affected. Scanners such as Trivy and Grype read VEX and stop reporting findings marked not_affected. Customers and auditors read the same file to see why. vexproof writes both common VEX formats: CycloneDX (1.6, or 1.7 on request) and OpenVEX 0.2.0.

vexproof makes two kinds of claim, at two levels of detail:

LevelClaimEvidenceTier
PackageNo file of the package is in the bundle.The package name is in the lockfile SBOM and absent from the bundle.Free
ModuleThe package is bundled, but none of the files holding the vulnerable code are.The bundler's own list of emitted files, checked against a rule naming the vulnerable files.Pro

It runs locally, in CI or on a laptop. It reads files and writes files. It makes network calls in three cases only: to the public OSV database when you don't pass a findings file or ask for alias lookup, to the npm registry when you run vexproof rules derive, and to GitHub's API when you run vexproof dependabot. Those requests carry package names, versions and advisory IDs. Your code and your build output are never sent anywhere, and vexproof never contacts Septakis. With a findings file and no alias lookup, a run makes no network calls at all.

Guide

Quick start

This walks through an npm project built with Vite. The bundler and package manager guides give the equivalent commands for other setups.

  1. Install vexproof 
    npm install --save-dev vexproof
  2. Add the plugin to your build
    vite.config.js
    import vexproof from 'vexproof/vite';

export default {
  plugins: [vexproof()],
};

    Build as usual. The plugin writes vexproof-modules.json in the project root, outside the deployed output.

    npx vite build
  3. List what you depend on 
    npx @cyclonedx/cyclonedx-npm --omit dev -o bom.lockfile.json
  4. Get the findings 
    npm audit --json --omit dev > audit.json || true

    npm audit exits non-zero when it finds anything, hence || true. You can skip this step: without --findings, vexproof queries OSV itself.

  5. Write the VEX 
    npx vexproof --lockfile bom.lockfile.json \
  --modules vexproof-modules.json \
  --findings audit.json \
  --openvex vex.openvex.json

Here is the output for the demo app in the repository, a dashboard that uses recharts and never imports lodash itself. recharts does, and three lodash advisories come with it.

vexproof: findings from audit.json (npm-audit) vexproof: bundle contents taken from the module map (25 packages) vexproof: 3 finding(s) → 1 not_affected (1 at module level), 2 in_triage → vex.cdx.json + vex.openvex.json in_triage GHSA-xxjr-mmjv-4gpg pkg:npm/lodash@4.17.21 ← vulnerable file(s) bundled: _baseUnset.js, omit.js not_affected (module) GHSA-r5fr-rjxr-66jc pkg:npm/lodash@4.17.21 in_triage GHSA-f23m-r3pf-42rh pkg:npm/lodash@4.17.21 ← vulnerable file(s) bundled: _baseUnset.js, omit.js

The _.template advisory is settled because template.js was never emitted. The two _.omit advisories stay open because recharts' Treemap imports lodash/omit, so the vulnerable files ship. Whether attacker-controlled input can reach them is a question for a person, and vexproof review records the answer.

The module-level verdict needs a Pro license. Without one, the same run settles only packages that are absent entirely, and prints how many open findings Pro would settle.

  1. Apply it in your scanner 
    trivy fs . --vex vex.openvex.json

    See Scanners for Grype and Dependency-Track, and Dependabot for GitHub's alerts.

Vite and Rollup

vite.config.js
import vexproof from 'vexproof/vite';

export default {
  plugins: [vexproof()],
  worker: { plugins: () => [vexproof()] },   // only if you ship web workers
};
rollup.config.js
import vexproof from 'vexproof/rollup';

export default { input: 'src/main.js', output: { dir: 'dist' }, plugins: [vexproof()] };

Every build that ships code needs the plugin: the main build, web workers, and any nested build() calls. Instances in one process merge into one file. Server builds (SSR) are skipped, because they don't ship to the browser; pass includeServer: true to record them too.

You don't have to get plugin coverage right by inspection. The plugin records its output folders, and vexproof refuses to run if a .js, .mjs or .cjs file in them wasn't recorded, naming each file. On Gitea's frontend this caught two bundles made by nested builds.

webpack and Rspack

webpack.config.js or rspack.config.js
const { VexproofPlugin } = require('vexproof/webpack');

module.exports = {
  plugins: [new VexproofPlugin()],
};

With webpack you can instead pass a stats file, as long as it lists every module:

webpack --json=stats.json

vexproof refuses a stats file that leaves modules out: a modulesSpace limit, grouped or filtered children, or a concatenated module (./x.js + 190 modules) whose members aren't listed. Any of those would make shipped code look absent. Rspack's --json flag always produces such a file, whatever the config says, so Rspack needs the plugin.

Angular

Angular 17 and later build with esbuild, and --stats-json writes its metafile:

ng build --configuration production --stats-json
npx vexproof --lockfile bom.lockfile.json --modules dist/my-app/stats.json …

esbuild

build.mjs
import * as esbuild from 'esbuild';
import { writeFileSync } from 'node:fs';

const result = await esbuild.build({ entryPoints: ['src/main.js'], bundle: true, minify: true, outdir: 'dist', metafile: true });
writeFileSync('meta.json', JSON.stringify(result.metafile));

Bun

bun build src/main.jsx --outdir dist --minify --production --metafile=meta.json

Bun writes the same metafile shape as esbuild. If you bundle with Vite under Bun, use the Vite plugin instead.

Bundle SBOM (optional)

With --modules, vexproof works out the bundle's packages from the module map. You can also pass a CycloneDX SBOM of the bundle with --bundle, for example from @cyclonedx/webpack-plugin. Then presence comes from that SBOM and file-level detail from the module map, and the two must agree.

Each package manager needs two commands: one for the lockfile SBOM, and one for findings. All of these were tested on the same app, and each reaches the same verdicts.

Notes by manager

Yarn 2+
Without --recursive, yarn npm audit checks direct dependencies only, and misses most of what ships. Plug'n'Play works: vexproof reads packages served from Yarn's zip cache and its __virtual__ paths as one copy per version.
Bun
With the isolated linker, cyclonedx-npm needs --ignore-npm-errors. The SBOM then also lists build tooling such as Vite. That doesn't change any verdict, since tooling never ships. bun audit doesn't report installed versions; vexproof takes them from the lockfile SBOM and keeps the ones inside each advisory's range.
npm
npm audit doesn't report installed versions either. vexproof takes every version of the package in the lockfile SBOM that falls inside each advisory's range.
pnpm
Store paths (node_modules/.pnpm/name@version/…) give each copy's version even when package.json isn't readable.

Where node_modules lives

vexproof reads each shipped package's installed package.json to learn its version. Run it from the project root, or pass --root pointing there. In a monorepo that is the folder the bundler resolved from, usually the app's own folder.

Guide

Scanners

Keep the scanner you have. vexproof reads its findings and writes VEX it applies. Scanners disagree on advisory IDs (Trivy reports npm issues by CVE, npm audit and Grype by GHSA), so every statement carries both, and one file matches either.

ScannerWriteApply
Trivy, any target--openvex vex.openvex.jsontrivy fs . --vex vex.openvex.json
Trivy, SBOM scan--out vex.cdx.jsontrivy sbom bom.lockfile.json --vex vex.cdx.json
Grype, SBOM or directory--openvex vex.openvex.json --openvex-package-productsgrype sbom:bom.lockfile.json --vex vex.openvex.json
Dependency-Track--out vex.cdx.jsonUpload after the lockfile SBOM has been analysed (below)
Other CycloneDX tools--out vex.cdx.jsonUpload beside the lockfile SBOM

Trivy

With OpenVEX, Trivy matches a statement when its product is the scanned project and its subcomponent is the vulnerable package. vexproof uses the lockfile SBOM's own component as the product, which is what Trivy sees as the project root. If yours differs, set it with --product.

With CycloneDX VEX, Trivy only applies statements that point into the exact SBOM it is scanning, by BOM-Link (urn:cdx:<serial>/<version>#<bom-ref>). vexproof writes those links from the lockfile SBOM, so scan that same file. Trivy keeps one CycloneDX statement per advisory ID, so prefer OpenVEX when two packages share an advisory.

Grype

On directory and SBOM scans, Grype only matches statements whose product is the package itself. --openvex-package-products adds that form to every statement. A file written this way says a package is unaffected in general, so use it only when scanning this app.

Dependency-Track

Dependency-Track applies a VEX only to findings it already has. Upload the lockfile SBOM, wait until its analysis is done, then upload the VEX. The API key needs BOM_UPLOAD, VULNERABILITY_ANALYSIS and, to create the project, PROJECT_CREATION_UPLOAD.

DT=https://dtrack.example.com; KEY="$DT_API_KEY"; NAME=my-app; VERSION=1.4.0
token=$(curl -sf -H "X-Api-Key: $KEY" -F autoCreate=true -F projectName=$NAME -F projectVersion=$VERSION \
  -F bom=@bom.lockfile.json "$DT/api/v1/bom" | jq -r .token)
while curl -sf -H "X-Api-Key: $KEY" "$DT/api/v1/event/token/$token" | jq -e .processing >/dev/null; do sleep 5; done
curl -sf -H "X-Api-Key: $KEY" -F projectName=$NAME -F projectVersion=$VERSION -F vex=@vex.cdx.json "$DT/api/v1/vex"

Each statement becomes an analysis with its state, justification and vexproof's reasoning as the details. Dependency-Track 4.x skips VEX entries that do not name a source, so vexproof names GITHUB for GHSA advisories (where Dependency-Track's GitHub and OSV mirrors both file them) and NVD for CVEs.

Dependency-Track applies a BOM-Link statement to every component in the project with that finding, not only the one linked. When two copies of a package get different verdicts on one advisory, vexproof writes the open statement last, so the copy that ships is never suppressed; both end up open for review.

Checking what a scanner will filter

In the repository, interop/live.sh runs the real Trivy and Grype on the demo app, with and without vexproof's VEX, and checks that each hides exactly the findings the VEX settles and still shows every other one. It covers Trivy fs and sbom scans with OpenVEX and CycloneDX 1.6 and 1.7, and Grype SBOM and directory scans, with VEX made from OSV and from each scanner's own report. Pass a version, such as interop/live.sh vexproof@0.12.0, to check a published package. It needs trivy, grype and network access.

interop/run.sh <dir> is the offline check: it applies the files with the same matching code Trivy and Grype use (openvex/go-vex, cyclonedx-go's BOM-Link parser, and Trivy's package-match rule), and prints what each would filter.

CI and the gate

Run vexproof after the production build and the SBOM step. The GitHub Action wraps the command; on other CI systems, call the CLI.

.github/workflows/release.yml (excerpt)
- run: npm ci
- run: npx vite build
- run: npx @cyclonedx/cyclonedx-npm --omit dev -o bom.lockfile.json
- run: npm audit --json --omit dev > audit.json || true
- uses: septakis-io/vexproof@v0
  with:
    lockfile: bom.lockfile.json
    modules: vexproof-modules.json
    findings: audit.json
    fail-on: in_triage
    license: ${{ secrets.VEXPROOF_LICENSE }}
- uses: actions/upload-artifact@v4
  with: { name: vex, path: "vex.*.json" }
.gitlab-ci.yml (excerpt)
vex:
  stage: test
  script:
    - npm ci && npx vite build
    - npx @cyclonedx/cyclonedx-npm --omit dev -o bom.lockfile.json
    - npm audit --json --omit dev > audit.json || true
    - npx vexproof --lockfile bom.lockfile.json --modules vexproof-modules.json
        --findings audit.json --openvex vex.openvex.json --fail-on in_triage
  artifacts:
    paths: [vex.cdx.json, vex.openvex.json]

The gate

--fail-on makes the run exit with code 1 when it trips. It never trips for any other reason.

in_triage
Fails when any finding is still open after automatic verdicts and recorded reviews.
new
Pro Fails only on open findings that weren't open or reviewed in the baseline. Needs --baseline; without it, the gate is skipped with a message.

A missing, invalid, expired or revoked license never fails a build. vexproof drops to free features and says so once.

Guide

Reviews and baselines

Some findings need a person: the vulnerable code ships, and someone has to decide whether it can be reached. vexproof review records that decision in the VEX file, with who made it and why. Reviewing is free.

npx vexproof review --vex vex.cdx.json --id GHSA-f23m-r3pf-42rh \
  --state not_affected --justification code_not_reachable --same-cause \
  --detail "omit() only receives a fixed key list from src/main.js" \
  --by "Jane Doe"

--id matches the statement's ID or any of its aliases, so the CVE works too. --same-cause applies the decision to every open finding on the same vulnerable files: GHSA-xxjr-mmjv-4gpg and GHSA-f23m-r3pf-42rh are both bugs in _baseUnset.js, so one review covers both. The review reference lists the states and justifications.

Reviews that follow their evidence Pro

On the next release, pass the reviewed file as the baseline:

npx vexproof --lockfile bom.lockfile.json --modules vexproof-modules.json \
  --findings audit.json --baseline previous/vex.cdx.json --fail-on new

A review is not tied to the lockfile or the version number. It is tied to what the decision rests on, which vexproof records on every open statement:

Vulnerable files
The shipped files holding the vulnerable code, each with a content hash.
Importers
The code outside the package that pulls those files in, found by walking the bundler's import graph back through the package's own files.

If both match, the decision carries into the new release, even across a version bump, keeping the reviewer, the date and the reasoning, and noting the version it was made for. If either changes, the finding goes back to the reviewer with the difference:

not_affected (carried) GHSA-f23m-r3pf-42rh pkg:npm/lodash-es@4.17.23 …after src/filters.js starts passing URL input to omit(): in_triage GHSA-f23m-r3pf-42rh pkg:npm/lodash-es@4.17.23 [new] ← the review by Jane Doe on 2026-09-27 needs re-confirming: new importer: src/filters.js
  • Decisions resting on things vexproof can't see (requires_configuration, requires_environment, and the protected_… justifications) stay tied to the exact version.
  • Reviews older than 365 days need re-confirming. Change it with --review-max-age <days>; 0 turns it off.
  • An automatic not_affected always wins over an older review, because it comes with fresh evidence.
  • A finding is new when it is open now and was neither open nor validly reviewed in the baseline. That includes a package that used to be absent and is now bundled, and a review that needs re-confirming. New findings are marked [new].
  • Matching uses every alias, so switching scanners (GHSA to CVE) doesn't lose decisions.
  • Import graphs come from the esbuild metafile, the Vite plugin and the webpack plugin. A module map without them falls back to matching the exact version.

Concept

How verdicts are made

vexproof starts every finding at in_triage and changes it only when the inputs prove absence. Each check below errs toward making no claim. They run in this order, and the first that applies decides.

#ConditionVerdict
1The finding's package URL can't be parsed.in_triage
2The bundle has no components at all. This almost always means a broken build or the wrong file.in_triage
3The package isn't in the lockfile SBOM, so vexproof has no basis for a claim.in_triage
4The package is in the lockfile SBOM and absent from the bundle.not_affected package level
5The package is bundled, and the module check below passes.not_affected module level Pro
6Anything else.in_triage with the reason

The module check

For a bundled package, vexproof settles a finding only when all of these hold:

  1. A module map was supplied, and the package is from npm.
  2. There is a rule for this package and this advisory, matched by ID or alias.
  3. The module map shows files from the package, agreeing with the bundle.
  4. The finding's version is one the bundle contains, and the copies at that version can be identified (see Multiple copies).
  5. No full build of the package ships from those copies (lodash.js, lodash.min.js, fp/ and similar), since a full build contains every function.
  6. None of the files the rule names ship from those copies.

Without a Pro license, findings that pass this check stay in_triage, and the run reports how many Pro would settle.

What the justification means

Both automatic levels use the CycloneDX justification code_not_present. The vexproof:level property says which level applied, and module-level statements also list the files that did ship. In OpenVEX, package level becomes component_not_present and module level vulnerable_code_not_present.

vexproof never writes code_not_reachable (OpenVEX: vulnerable_code_not_in_execute_path), the justification reachability analysis uses. That one says the code ships but is never called, which is an inference about your program. code_not_present says the code is not in the artifact, which anyone can check against the build output. A person can still record code_not_reachable with vexproof review.

Concept

Multiple copies

A package can ship more than once, at different versions: npm nests conflicting versions, and pnpm and Bun keep one folder per version in their store. A file-level claim is only sound if it checks the copy at the vulnerable version.

vexproof groups shipped files by the folder they came from, and reads each folder's version from, in order:

  1. its installed package.json, under --root;
  2. the store path: .pnpm/name@version/, .bun/name@version/, or a Yarn cache archive named name-npm-version-….zip.

It then checks the finding against the files of the matching copies only. A vulnerable file shipping from a fixed copy doesn't block the verdict; one shipping from the vulnerable copy always does. The statement names the copies checked in vexproof:copies-checked.

No claim is made when several copies ship and any copy's version can't be read, when no shipped copy is at the finding's version, or when a single copy's installed version disagrees with the finding.

On Gitea's frontend, lodash-es ships at 4.17.23 and 4.18.1. The 4.17.23 advisories were checked against that copy's files alone.

Concept

Derived rules Pro

Hand-checked rules cover lodash and lodash-es. For other packages, vexproof can derive a rule from the fix itself: the runtime files that changed between the version you have installed and the first release outside the advisory's range. If none of those files shipped, the fix touched no code you ship.

npx vexproof rules derive --lockfile bom.lockfile.json --findings audit.json \
  --modules vexproof-modules.json
npx vexproof --lockfile bom.lockfile.json --modules vexproof-modules.json \
  --findings audit.json --rules vexproof-rules.derived.json

The diff runs from the installed version, not from the last vulnerable release. Advisory ranges can be wider than the real fix: lodash-es fixed GHSA-xxjr-mmjv-4gpg's code in 4.17.22, a release inside the advisory's range, so the narrow diff would show only unrelated files and wrongly clear shipped code.

Why they only suggest

A fix can change a caller, for example by adding validation in an entry file, while the vulnerable code sits in a file it didn't touch. So a derived rule leaves the finding in_triage and puts its reasoning in the detail. It settles the finding only when the run passes --accept-derived, or when someone records a review. Accepted statements carry vexproof:rule-origin.

vexproof makes no rule when the fix changed no JavaScript (a dependency update), or when more than half the package's files moved before the fix.

How well they work

CheckResult
10 lodash and lodash-es advisories with hand-checked rulesEvery derived rule contains the file with the vulnerable code.
Angular, recharts and Gitea buildsNever cleared a finding the hand-checked rules keep open. Settled 4 fewer, because a fixed release that bundles several fixes yields one broad rule.

Concept

Apps with a server

In an app with server-side rendering, code also runs on a server, and packages used only there are absent from the browser bundle while still running in production. For these apps, point vexproof at what you deploy.

npx vexproof --lockfile bom.lockfile.json --findings audit.json \
  --deploy .next/standalone --deploy .next/static     # Next.js, output: 'standalone'
npx vexproof … --deploy .output                        # Nuxt / Nitro
npx vexproof … --deploy build --deploy node_modules    # runs with its node_modules, after npm prune --omit=dev

A deployment folder is evidence in the same sense as a browser bundle: a file that isn't deployed can't run. vexproof reads two things in it:

Deployed package files
Files the framework copied into its output, such as Next's traced standalone/node_modules or Nitro's .output/server/node_modules. Nitro copies individual files, so file-level evidence holds there too.
Bundled code
Each bundled file's source map, which names every original file bundled into it.

Turn source maps on for the build:

FrameworkSetting
Next.jsproductionBrowserSourceMaps: true, experimental: { serverSourceMaps: true }, output: 'standalone'. The standalone folder doesn't copy server maps; vexproof finds them in .next.
Nuxtsourcemap: { server: true, client: 'hidden' }
Vite, SvelteKitbuild.sourcemap: 'hidden'

Maps outside the deployment folders are found with --maps <folder>. You can delete .map files from the public output after vexproof runs.

What it refuses

  • A bundled file with no source map, unless it is an exact copy of an installed file (Next's polyfills) or glue code with no functions of its own (manifests, Next's server.js).
  • Bundled code that loads a lockfile package at runtime when that package isn't inside the deployment. Imports are parsed, so examples in comments and strings don't count, and packages linked under hashed names are followed to the real package.
  • A source-map source that can't be traced to an installed package.

A package that publishes its own source maps is taken whole. Bundler maps point through them at its original sources, not the files that shipped (esbuild followed fast-equals' maps to src/comparator.ts), so its file-level rules can't be checked.

Results on real apps

AppFindingsSettledStill open, because the server runs them
Next.js 16, Turbopack, standalone179: lodash files not bundled; build-only postcss and @babel/traverse not deployedjs-yaml, marked, semver (imported by next.config.mjs, which Next deploys)

On the recharts demo, the files named by source maps match the bundlers' own module lists file for file (Vite 8, webpack), and on esbuild once fast-equals is traced back through its maps.

Without a server deployment

vexproof refuses to run when the module map records a skipped server build, or the lockfile includes Next.js, Nuxt, SvelteKit, Remix, React Router's server runtime, Angular SSR, Vike, SolidStart, TanStack Start, Astro's Node adapter or Analog. --browser-only writes VEX for the browser bundle alone and marks it vexproof:scope = browser-bundle; give that artifact its own identifier with --product.

Dependabot

Dependabot reads no VEX, so an alert for code that never shipped stays open. vexproof dependabot applies a VEX file to a repository's npm alerts through GitHub's API.

vexproof dependabot --vex vex.cdx.json --lockfile bom.lockfile.json --dry-run
OptionMeaning
--vex <file>The CycloneDX VEX vexproof wrote. Repeatable.
--lockfile <sbom>The lockfile SBOM that VEX was made from, matched by the hash the VEX records. Repeatable.
--manifest <path>A manifest file or a folder whose alerts to change. Repeatable. Default: the current folder.
--repo owner/nameDefault GITHUB_REPOSITORY, then the git origin.
--token <token>Or VEXPROOF_DEPENDABOT_TOKEN, GH_TOKEN, GITHUB_TOKEN.
--dry-runPrint what would change.

What it changes

Dismiss
An open alert whose package versions in the vulnerable range are all not_affected or false_positive in the VEX. The comment starts with vexproof:, gives the reason and links to the run. A version the VEX says nothing about keeps the alert open.
Reopen
An alert vexproof dismissed that a later VEX no longer settles.
Left alone
Alerts a person dismissed, alerts with a dismissal request waiting for approval, development dependencies, and alerts on manifests outside --manifest.

Token

The token needs "Dependabot alerts" read and write: a fine-grained token or a GitHub App token. A workflow's own GITHUB_TOKEN can read alerts (permissions: vulnerability-alerts: read) but cannot change them, so it only works with --dry-run. In Actions, only a run of the default branch changes alerts, because Dependabot alerts describe that branch; other runs preview. A VEX written with --browser-only is refused.

Exit codes: 0 when the sync ran, 2 when it could not (token, repository, a VEX that does not match the lockfile) or an update failed.

Module rules

A rule names the files of a package that hold an advisory's vulnerable code, or are the public entry to it. Module-level verdicts are only as good as their rules, so each one is checked against the package source before it ships. Rules live in src/pro/rules/module-rules.json inside the package, versioned by date (currently 2026.09.26). Extra rules load with --rules; derived rules use the same schema, with origin, versions and derivedFrom added.

License keys

A license key is a signed token, vxp1.<payload>.<signature>, verified on your machine against a public key built into vexproof. The payload names the organization, the features and the expiry date. vexproof looks for it in this order:

  1. --license, a token or a path to a file holding one;
  2. the VEXPROOF_LICENSE environment variable, likewise;
  3. a .vexproof-license file in the working directory.
  • License checks make no network calls. Verification is local.
  • After expiry there is a 14-day grace period with a warning on each run.
  • A license can be revoked before it expires. Each vexproof release carries a list of revoked license ids, so a revocation applies from the first version that includes it.
  • A missing, invalid, expired or revoked license never fails a build. vexproof runs free features and says why, once.
  • The licensed organization is recorded in the VEX, and is the OpenVEX author.
